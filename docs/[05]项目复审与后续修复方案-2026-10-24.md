## 5. 新增问题的证据与修复设计

### A15：PrintJobId 属性类型错误

微软打印管道属性包规定 PrintJobId / XPS_FP_JOB_ID 为 VT_UI4。InitializeFilter 只接受 VT_I4，并读取 lVal，符合标准的 VT_UI4 / ulVal 会被忽略，使初始值 job_id_=0 保持不变。

后续元数据与页面索引直接使用 job_id_，文件名也使用该值。同打印机的不同任务因此可能写入同一个 job-<printer>-0-pt-metadata.json；UI 无法将其可靠归入真实非零作业。现有 mock 使用 VT_I4，掩盖了接口不匹配。

修复设计：

1. 优先按标准常量、VT_UI4 和 ulVal 读取；如保留 VT_I4 兼容，只接受明确有效的正数并记录兼容来源。
2. 缺失、错误类型或零身份应显式报告不可关联，禁止以共同的 0 身份发布可消费消息；保留独立诊断，不影响原文档透传。
3. 抽取可单测的属性读取函数，复用既有 COM 管理；测试 mock 必须独立依据 SDK 契约构建。

验收：覆盖 VT_UI4、UINT32_MAX、合法/非法兼容类型、缺失和零值；非空打印流的元数据 job_id 与输入一致，不同任务不会共享 0 文件，最终桥接能关联回正确作业。

依据：[Microsoft Learn：Print pipeline property bag](https://learn.microsoft.com/en-us/windows-hardware/drivers/print/print-pipeline-property-bag)。本机 SDK filterpipeline.h 中的属性名常量也与文档一致。

### A16：自动安装成功判定与服务控制不可靠

主窗口构造末尾调用 ensureFilterInstalled；管理员且无 sentinel 时直接执行 tryInstallFilter。它忽略 DLL 复制、DLL 注册、备份、配置写入及服务控制的重要返回值，即使没有找到/成功更新任何目标管道，仍写入 sentinel 并返回 true。后续启动只要 sentinel 存在就跳过检查，界面可能持续显示“捕获已就绪”。

服务句柄仅申请 SERVICE_STOP | SERVICE_START，第 361 行却调用 QueryServiceStatus；该 API 需要 SERVICE_QUERY_STATUS，现有句柄权限不足。代码没有检查查询失败，也不确认 StartServiceW 成功及服务最终运行状态。

配置写入使用 CREATE_ALWAYS 截断后直接 WriteFile，未检查完整字节数、最终持久化或实施失败后的回滚。捕获安装失败不应演变成破坏现有打印配置的路径。

修复设计：

1. 将安装与探测从 MainWindow 提取为可注入系统接口的安装服务，GUI 仅展示结构化结果并调用。
2. 分别验证产物路径/身份、复制、COM 注册、目标管道发现、备份、修改和加载条件；不把零目标或部分失败标为全成功。
3. 使用 XML 解析及同卷原子替换，备份成功才允许修改；失败恢复旧配置并保留诊断。
4. 单纯启动应用不自动重启打印服务。安装需要重启时明确显示操作及影响，执行时申请查询权限并检查每一步和最终状态。
5. sentinel 改为带版本、DLL 哈希及目标配置结果的记录；启动重新探测，记录不能替代健康检查。

验收：以 fake 系统接口覆盖复制失败、注册失败、零目标、部分写入、备份失败、停止/启动超时、旧 sentinel；失败不得产生成功状态或破坏原配置。真实安装与服务重启仅在后续约定的隔离设备环境验证。

依据：[Microsoft Learn：QueryServiceStatus 的访问权限与错误返回](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-queryservicestatus)。未在用户机器执行服务变更来复现此问题。

### A17：普通退出缺少数据保存屏障

closeEvent 只询问是否退出，选择“是”立即 accept。析构时停止监听、短暂 processEvents 后调用返回 void 的 flushSave，不检查 hasPendingSave；BillingService 析构再次 flush 后也无法阻止退出。

此外，日切/读写故障时事件进入 deferred_events_，只在每秒定时器中重放。flushSave 不处理该队列；hasPendingSave 仅反映 dirty_。因此普通退出既可能遗失保存失败的任务修改，也可能遗漏尚未重放的作业。此风险不限于 [04] 中记录的强制终止或断电限制。已成功持久化的冻结订单不因此自动丢失，本项针对仍在内存中的工作。

修复设计：

1. 业务层提供可观察的 prepareShutdown/flushAndDrain 结果，涵盖日切暂存、未保存桶、待投递事件与 writer 状态，不能仅检查 dirty_。
2. 在窗口仍可保留时停止产生新事件、有序收齐已投递工作并按原业务日重放，再落盘；全部成功后才允许 accept。
3. 失败保留窗口和内存，展示具体失败与重试/导出恢复数据入口；不能只在析构函数中补救。恢复包须保留事件原日期和物理身份。
4. 析构仅保留兜底，不作为可恢复保存流程；正常退出不依赖固定 100ms 事件泵证明完成。

验收：正常退出、最终 Replace 失败、故障后待重放事件、恢复但未等到下一秒定时器、停止监听时仍有 queued 信号等场景；失败不退出，恢复重试后数据与重启读取一致，跨日事件仍归原日期。
