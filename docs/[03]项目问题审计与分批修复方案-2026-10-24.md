## 5. 问题证据与修复设计

### A01：过期清理删除历史订单

证据：cleanupExpiredCapturedData 对早于 cutoff 的整个 YYYY-MM-DD 目录调用 removeRecursively。schema v4 的 orders.json 正在同一个目录内。默认 retention_days=90，构造主窗口和启动监听时都会触发清理。ARCHITECTURE 明确要求保留结算历史。

触发与影响：有超过保留期的新版日桶时，普通启动即可删除该日权威订单文件；新版订单没有旧 history 双写副本，不能假定可以恢复。

修复：将清理策略提取为后端存储函数，只清理明确列出的捕获子目录及临时产物，始终保护 orders.json、备份与迁移记录。存在账务文件的日期目录不得整目录递归删除。捕获保留期与订单归档策略分别定义；未明确授权订单删除时保持订单永久保留。

验收：隔离目录中构造过期捕获与订单、近期数据、配置和 _state，执行真实清理函数后，只有过期捕获消失；所有订单及非捕获文件哈希不变。

### A02：读取失败后覆盖原账务文件

证据：loadBatchesFromFile 在 ifstream 打开失败时直接返回“缺失文件”的成功空状态，不能区分不存在与拒绝访问；解析失败则返回 false。BillingService::load 没有设置禁止写入或恢复状态。之后接收新作业、scheduleSave/flushSave，仍会用当前内存全量替换同一路径。仓储也未校验 schema 版本、必需根字段或完整订单集合，部分非法订单会被静默跳过。

触发与影响：截断 JSON、存在但读取失败、无法识别的新 schema、订单解析失败等情形下，界面可能按空状态运行，下一次保存覆盖可恢复的原文件；重启后可能失去既有订单。

修复：仓储返回 Missing、Loaded、Corrupt、AccessDenied、UnsupportedSchema 等明确结果；解析到临时对象并完整校验后才能提交。损坏/拒绝访问时保留原文件、尝试最后可读备份，并将该桶置为写保护。恢复失败必须向 UI 提供明确状态，禁止覆盖原桶。

验收：分别注入不存在、截断、无权限、缺少 tasks/orders、非法订单、未知 schema；损坏数据原文件哈希不变，不得以空日桶覆盖。可读备份恢复后再允许保存。

### A03：跨午夜未切换权威桶

证据：setOrderBucketPath 在初始化或手动启动监听时绑定路径；flushSave 每次却用实时 todayDateString 写 business_date。未发现常驻日期切换协调器，监听器的 outputDir 也在启动时固定。

触发与影响：程序在 D 日启动并运行至 D+1 日，新日期任务号/订单号与 D 日 orders.json 混在一起，文件内部日期还会变成 D+1。正常重启又会改读 D+1 日目录，跨日运行期间写入 D 日路径的新日订单不会出现在对应新日历史中。

修复：引入可注入的 BusinessDayCoordinator，统一持有当前已绑定业务日；写入前验证路径日期与数据日期一致。换日先成功刷完旧桶，再切换新桶、索引、计数器与采集输出目录；失败时禁止继续以新日期写旧路径。跨日未结算状态遵循现有业务规则，但旧日结算历史不得清空。

验收：通过注入时钟模拟 23:59:59→00:00:01，无须修改系统时间；分别覆盖持续监听、停止再启动、恢复失败和旧日未结算任务，检查路径、日期、单号与历史查询一致。

### A04：保存成功不能代表最终写入成功

证据：BillingBatchRepository::save 与 CounterStore::saveLocked 在流尚未关闭前检查 !out，随后依赖析构关闭并 replace_file；关闭时错误无法反馈。AppConfig::save_to_json 在替换前甚至没有等价的最终流状态验证。共用 write_text_file_atomic 虽检查 flush/close，但其 FlushFileBuffers 返回值未检查，关键日桶当前也未复用该函数。

触发与影响：磁盘满、最终缓冲写回失败等场景可能把不完整临时文件替换为正式文件，并误报成功；结算状态会据此提交。

修复：统一复用原子文件写入函数，验证 write、flush、close，以及 Windows 刷盘错误；失败不替换旧文件。临时路径用原生 filesystem::path 追加后缀，保留可读备份并返回结构化错误。日桶、计数器、配置按相同契约处理。

验收：通过可注入文件 I/O 接口，在写入、flush、close、刷盘与 replace 各阶段失败；旧文件字节不变，结算不成功，内存状态正确回滚，并保留可诊断错误。

### A05：已结算批次金额漂移

证据：onMetadata、onLifecycleEvent 和 setColorPages 没有与 setManualPrice 相同的“已结算禁止修改”保护，仍重算作业和批次。冻结的 settlementOrders_ 不会同步变化。

触发与影响：在打印结束前结算，随后到达页数、份数、PrintTicket 或操作者修改彩页数时，任务列表的金额可改变，而历史订单金额仍为冻结值，导致已结算批次明细与冻结订单出现两个金额来源。todayRevenue 当前只统计未结算批次，不将其作为本问题的直接影响范围。

修复：明确分离采集状态与冻结计费快照。已结算任务允许继续更新打印进度，但不允许改写冻结价格、结算页数和批次财务汇总；所有人工改价入口采用同一状态校验。需要调整已结算订单时应另建显式调整业务，不能隐式重算。

验收：结算后再送入不同页数、份数和颜色的元数据、生命周期事件、彩页编辑；订单、财务汇总及重启后的金额保持一致，打印进度仍可刷新。

### A06：PrintTicket 消费竞争与错误去重

证据：每个 printerLoop 都扫描 outputDir、其父目录和环境变量目录；scan_one_dir 在回调后删除文件，没有唯一消费或原子认领机制。每条监听线程启动还会以空回调清理这些目录。seen_pt_jobs 的键只有 printer_name 与原始 JobId，贯穿整个监听会话。

触发与影响：两个线程可能重复读取同一文件；一个新启动线程可能删除其他活动线程尚未消费的有效元数据。JobId 在同一会话复用时，后一个物理作业的 PrintTicket 会被去重掉。扫描失败也可能因 exists/is_regular_file 的异常冒出而结束监听循环。

修复：集中为单一 PrintTicketInbox 消费器，文件先原子认领，再解析并按打印机路由；成功交付后确认删除，失败隔离保留并重试。取消“无条件启动清空”，过期判断依据作业身份和生成时间。消息身份应携带提交身份/物理作业标识或生产者生成的唯一 token，不能只依赖原始 JobId。

验收：并发启动两个监听器、停止重启其中一个、重复读取、重复消息、原始 JobId 复用、读权限暂时失败，确保有效消息不丢失、重复交付无额外计费、复用作业不被忽略。

### A07：捕获失败损伤打印透传

证据：StartOperation 将捕获处理和 SendXpsUnknown 放在同一个 try 内。捕获 std::exception/bad_alloc 时释放 part 后继续下一项，当前 part 未转发。GetXpsPart 失败时 break，SendXpsUnknown 失败未作为终止错误处理，末尾仍固定 return S_OK；CloseSender 的结果也未校验。

触发与影响：采集解析/内存分配异常可能使页面丢失；下游失败可能被报告为正常完成。当前空流水线测试无法触发这些路径。

修复：用 RAII 保持 part 生命周期，将可选捕获异常隔离在独立边界，尽力保持原 part 透传；读取/转发/关闭失败保存并传播真实 HRESULT，统一关闭与 FilterFinished 收尾，明确取消状态。不能通过跳过页面实现“采集失败不影响打印”。

验收：非空 Job/Document/Page 序列逐项核对透传数量与顺序；注入捕获异常仍正常透传；注入 provider/consumer/close 失败时返回正确错误且无 COM 泄漏；验证取消与完成只收尾一次。

Windows 接口行为核对依据：Microsoft Learn 的 SendXpsUnknown 返回 HRESULT，ShutdownOperation 用于取消/错误并要求最终 FilterFinished。

- https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/filterpipeline/nf-filterpipeline-ixpsdocumentconsumer-sendxpsunknown
- https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/filterpipeline/nf-filterpipeline-iprintpipelinefilter-shutdownoperation

### A08：页面索引指向不存在的文件

证据：过滤器生成 job-...pt.xml 等带点号的索引引用；persist_payload_files 对整个文件名调用 safe_filename_token，该函数会把点号变为下划线。例如索引中的 job-X-1.pt.xml，实际写成 job-X-1_pt_xml。另在页面 payload 构造中只填充 PrintTicket XML，未填 fixed_page_xml；索引却始终声明 .fpage 路径。

触发与影响：即使 PrintTicket 实际写出，按索引查找也失败；FixedPage 索引可能指向从未生成的实体。

修复：将“打印机标识编码”与“安全文件名验证”分离，生成唯一、统一的文件名后同时用于引用与写盘。实现需要承诺的 FixedPage 实体提取；无法提供实体时显式记录 unsupported/未捕获，不生成虚假可用引用。

验收：用一个真实非空 mock 页面生成产物，逐条打开所有非空索引引用并核对内容；包含 Job/Document/Page PT、FixedPage、空 PT、多文档、中文打印机名和安全路径验证。

### A09：打印机令牌碰撞覆盖数据

证据：safe_filename_token 将所有非字母数字、连字符、下划线的字节替换为下划线。“HP A”和“HP_A”输出完全相同；UTF-8 中文打印机名会大量退化为下划线。令牌被用于 latest、jobs 和过滤器文件路径。

触发与影响：同一目录下，不同打印机可能写入同一个 latest 桶或同名 PrintTicket 文件；JobId 相同时覆盖尤其直接。新增内部 JobId 映射不能消除过滤器使用外部 JobId 时的路径碰撞。

修复：采用可恢复编码或“可读前缀+固定算法稳定摘要”形成持久标识；不要使用不保证跨进程稳定的 std::hash 作为存储身份。保留原始打印机名字段，对旧目录提供只读兼容映射。

验收：空格/下划线、斜杠/反斜杠、同字节长度中文名、相同外部 JobId 的多打印机并发，所有归档与消息均唯一且重启后一致。

### A10：旧结算副本混入今日桶

证据：migrateLegacyDailyStateIfNeeded 从 history 按日期迁移后，又枚举 _state/settlement_orders 下所有 JSON，将成功读取的订单无日期过滤加入今日 orders。旧状态目录可能保存多天副本。

触发与影响：升级后首次创建今日桶时，旧日订单也被写入今日桶，可能在历史桶和今日桶重复出现，造成日期归属与统计错误。存在目标桶即跳过也没有完整性核验或迁移完成标记。

修复：独立迁移器先读取全部来源，按明确业务日归档，使用订单号、任务号及内容完整度检查冲突；无法确定日期的订单保留到隔离待核对清单。写入并校验后记录来源与迁移标记，重试必须幂等，原文件不删除。

验收：跨三日旧数据、history/_state 双副本、冲突金额、损坏副本、迁移中断与重复启动，不得把旧日订单归入今日，不重复、不静默取错。

### A11：安装脚本在 PowerShell 5.1 解析失败

证据：脚本第一行声明 #requires -Version 5.1，第 105 行为 Resolve-Path 表达式后接 ?.Path。本机 Windows PowerShell 5.1.26100.9711 的 AST 解析明确返回“表达式或语句中包含意外的标记 ?.Path”。

影响：脚本在执行安装步骤前已解析失败，DryRun 同样无法运行。用户按项目指南使用系统 PowerShell 安装会被阻断。

修复：改用 PowerShell 5.1 支持的显式判空；同步核对默认 DLL 路径与 [02] 新 Release 目录的实际产物关系，优先接受明确产物路径，不递归选任意旧 DLL。

验收：PowerShell 5.1 和可用的 PowerShell 7 均通过 AST 解析；无管理员副作用的路径/参数逻辑先测试，再在用户批准的安装环境验证 DryRun 和实际安装。

### A12：异步存储故障无法恢复且资源无控制

证据：快照和页面 writer 的 catch 在整个工作循环之外。一次文件 I/O 失败就退出 worker 并置 running=false；已弹出的失败项没有重入队。enqueue 使用无界 deque；queue_capacity 只影响一次日志输出。桥接层把 enqueue=false 泛称为队列满，未区分 writer 已退出和磁盘错误。

触发与影响：暂时文件锁或权限问题可以导致后续整个监听会话持续不落盘；生产速度长期超过写盘速度时内存继续增长。stop 的补写也不保证找回已经弹出并失败的那一项。

修复：按项捕获故障、有限退避并保留失败项，提供明确健康状态和错误分类；对可覆盖快照按作业合并，必须保留的事件采用磁盘暂存和可观测背压，不能静默丢弃账务数据。沿用“不限制业务记录总量”的需求，同时控制内存中的待写工作量。

验收：一次瞬态写失败后自动恢复、持续失败时可见告警、恢复后失败项补写、停止时完整 drain；慢盘压力场景测量队列、RSS、延迟，并约定资源阈值。

### A13：WithQt 指向另一套构建与测试

证据：build-msvc.ps1 的 WithQt 仅把 configure preset 改为 vs2026-x64-qt，BuildPreset/TestPreset 仍设为 vs2026-debug；CMakePresets 中该预设绑定 vs2026-x64，且关闭 UI。脚本不逐步检查 LASTEXITCODE。

触发与影响：调用 -WithQt 可能只配置 Qt 目录、实际构建并测试非 Qt 目录；前一步失败后仍继续执行，最终成功状态不能证明目标 GUI 已生成。

修复：给 Qt Debug 配置配套 build/test preset，并校验三者对应同一构建目录；复用 [02] 打包脚本已有的本机命令失败传播规则，提取通用 PowerShell 函数库后由业务脚本调用；统一处理进程级 LANG 冲突，不修改永久系统配置。

验收：WithQt 产物和测试确在 Qt 目录，账务服务测试实际参与；给配置、编译、测试分别模拟非零退出码，后续步骤不执行且脚本返回失败。

### A14：静态检查不能可靠阻断失败

证据：run-static-analysis 未逐步检查本机命令退出码；cppcheck 没有 --error-exitcode；缺工具、缺 compile_commands 仅警告。脚本也未配置 Qt 宏。当前环境 clang-tidy 不在 PATH。

影响：检查未执行、解析不完整或实际发现问题时，脚本依然可能表现为完成，不能满足 readme 的发布检查标准。

修复：区分严格发布模式与明确的局部检查模式；严格模式必须验证工具、编译数据库与分析配置，合并所有步骤退出码，任一必要项未执行则失败。配置 Qt/Win32 并优先使用实际构建目标的编译数据库，告警抑制必须逐项记录依据。

验收：工具缺失、编译数据库缺失、分析器非零、预置可识别缺陷均返回非零；正常检查通过才返回零；被跳过的检查有明确记录。

## 6. 额外维护观察

这些观察不重复计入 14 项业务/工程问题：

1. print_watcher.cpp 2050 行、main_window.cpp 1718 行、billing_service.cpp 1656 行、watcher_bridge.cpp 1144 行。MainWindow 仍混合安装、迁移、清理、监听和界面；BillingService 混合存储与计价编排。建议在正确性修复稳定后单独批准结构拆分，不借修复扩大重构。
2. 多处通过 path.string()+后缀构造临时路径，并使用 narrow 环境变量接口，存在当前 Windows 代码页不能表达的路径风险。应在 A04 一并采用原生 path/wstring；回归覆盖中文、非当前代码页字符和表情目录。
3. 多套自写 JSON reader 对 Unicode 转义、数值范围、完整 schema 的支持不同。日桶 JsonReader 对未识别转义直接保留转义字母，例如外部工具写入的 Unicode 转义可能失真。应集中账务序列化边界并测试标准 JSON 往返；是否引入库需在修复批次确定。
4. 旧指南中的 per-batch 文件、GUI 计价位置与当前实现存在漂移；应以本次修复的最终行为更新指南，并保留历史记录。
5. 空过滤器测试、少量服务测试与 1k/2k 存储压力测试不足以证明真实打印正确性、覆盖率 ≥80%、10000 真实任务、50ms 延迟或 30 天稳定性，本轮不作这些验收结论。
